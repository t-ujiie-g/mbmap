# AGENTS.md — mbmap

Tool-agnostic contributor & AI-agent guide (Claude Code, Codex, Cursor, …).
`CLAUDE.md` is a symlink to this file, so there is exactly one guide to maintain.

mbmap: a MoonBit vector-tile map rendering engine for the Web, aiming to be lighter and faster than MapLibre GL JS.

- `docs/VISION.md` is the authoritative spec: goals, perf targets (§2), architecture (§3), design principles (§4), scope (§5), API (§6), work rules (§7), phase plan (§8).
- `PROGRESS.md` records per-phase results, benchmark numbers, known issues and user decisions. Read both before starting a phase.
- `docs/FORMATS.md` is the reference for the binary formats and worker messages; code cites its section names instead of restating layouts.
- `docs/CLOUD.md` is how to set up and use Claude Code on the web (environment, network, setup hook); §9 has what changes there.
- If a task is not in the current phase of VISION §8, confirm scope with the user before widening it.

MoonBit skills (`moonbit-agent-guide`, `moonbit-orientation`, `moonbit-refactoring`, …) come from the `moonbit-skills` plugin (`/plugin` → marketplace `moonbitlang/skills`). They auto-engage in `.mbt` files.

## 1. Commands

MoonBit (run from repo root):

```sh
moon check --target all          # type-check every backend (wasm, wasm-gc, js, native)
moon test --target all           # all tests on all backends
moon test <pkg-dir> --target all # one package, e.g. moon test bench/backend/kernel
moon test <pkg-dir> -F "glob"    # filter tests by name
moon test <pkg-dir> -u           # update snapshots (single target only; -u fails with --target all)
moon fmt && moon info            # before committing; regenerates pkg.generated.mbti
```

npm package (from `npm/`): `npm ci && npm run build` writes `dist/` (index.js + .d.ts, worker.js, mbmap.wasm); `npm run size` checks the gzip budgets of VISION §2; `npm test` runs the unit tests (`npm/test/*.test.ts`, `element/*.test.ts` and the `*.test.mjs` of `worker/js`, `geojson_worker/js`, `wasmio/js`, `data_worker/js`) with Node type stripping, so modules under test must be import-free or import other files with their extension (`./images.ts`, `./style.ts`, `./urls.ts`, `./camera.ts`). `worker/js/mirror.test.mjs` checks the constants JS mirrors from MoonBit (`KIND_*`, `LAYER_ENTRY_WORDS`, `ENTRY_*`, label columns).

## 2. Workflow

How the user works with agents (standing instructions; they hold in every session, local or on the web):

- Reply to the user in Japanese, short status lines and `AskUserQuestion` dialogs included. Code, identifiers, commit messages and PR descriptions stay in English.
- Each step ends the same way: validation (below), commit, push, a PR, CI green, then a short Japanese report of what changed, measured results and open questions, and stop. The user merges and answers 「マージしました」 (often with 「続けて下さい」); never start the next step before that. When several PRs are ready, report and get them merged one at a time, merging `main` into the next before reporting it.
- Phase starts, budget changes and design changes are asked with `AskUserQuestion`, with a recommended option first.
- Use parallel agents wherever the work splits (see "Parallel work" below): the user prefers starting independent lines at once over proposing them and waiting.
- Never force-push or amend a pushed commit; to bring a branch up to date, merge `origin/main` into it.

- Never commit to `main` directly: `git switch -c <kind>/<short-description>` (`feat/`, `fix/`, `chore/`, `docs/`, `refactor/`, `phaseN/`), then `gh pr create`.
- Validation loop before reporting complete or committing:
  ```sh
  moon check --target all
  moon test --target all
  moon fmt
  moon info                            # commit .mbti diffs with the code
  ```
  A `.mbti` diff means the public API changed; check it is intended.
  Then the JS side: `npm --prefix npm run build && npm --prefix npm test && npm --prefix npm run size`, `npm --prefix bench test`, `npm --prefix bench run npm:pack` (CI runs it), the goldens of the area touched (§1), and `node bench/lib/long-comments.mjs`.
- Phases (VISION §8): confirm a phase's scope, steps and completion criteria with the user before starting it, and deliver it in steps (one PR each, e.g. 13.1-13.4). When a phase is complete, run a refactoring and security review (§7, §8) over what it added before starting the next phase. PROGRESS.md opens with where things stand.
- A change that claims a perf effect reruns the relevant `bench/` script and updates PROGRESS.md with the new numbers.
- Major design changes (Wasm backend, package split, rendering approach) require presenting measurements and options and getting user confirmation first (VISION §7).
- Parallel work: at the start of a phase or step, look for work that does not depend on the main line (research for the next phase, leftover known issues, benchmarks) and start it alongside, saying what was split off.
  - Research runs as a read-only subagent that reports back. The findings go into VISION/PROGRESS when that phase starts, never into a separate planning doc.
  - Code runs in its own git worktree and branch (`Agent` with `isolation: "worktree"`, or `git worktree add ../mbmap-<name> -b <branch>`). Each worktree needs `npm ci` in `bench/`, `npm/` and `examples/react/`, and a copy of `bench/fixtures/` (gitignored). `_build/` is per worktree, and `bench/lib/serve.mjs` picks a free port, so pack tests can run side by side.
  - Keep apart: work that must wait for a confirmation (a phase's scope, the review after a phase), and work touching the same files as the main line. Files that often conflict: the top of `PROGRESS.md`, `AGENTS.md`, `npm/scripts/size.mjs`, `bench/npm/pack-test.mjs`, `examples/shared/*`, `npm/src/ui.ts`. Merge `main` into the branch before reporting the PR.
  - Never run performance benchmarks in parallel: they compete for the GPU and CPU. Agents that measure take a lock around each run (`until mkdir "$TMPDIR/mbmap-bench.lock" 2>/dev/null; do sleep 5; done; …; rmdir "$TMPDIR/mbmap-bench.lock"`), and the main line reruns the final numbers alone.
  - Each line of work is still one PR per step, reported and merged one at a time.

## 3. Toolchain notes

- moon 0.1.20261104 uses the **new DSL config files `moon.mod` / `moon.pkg`**, not `moon.mod.json` / `moon.pkg.json`. MoonBit syntax and tooling change quickly: verify APIs with `moon ide doc`, generated `.mbti`, or docs.moonbitlang.com instead of guessing from memory.
- `bench/backend/entry` shows the working patterns for exports (`pkgtype(kind: "foreign_library")` + `#export_name`), `export-memory-name`, and per-file conditional compilation (`options(targets: {...})`).
- `moon info` writes `.mbti` from the canonical backend (wasm), so js-only packages (`map`, `render_webgl2`) currently get none; `moon info --target js` only prints the diff against wasm. Settle how to track their interface before they gain public API.
- Inline wasm via `extern "wasm" fn f(...) = #|(func ...)` works on both wasm and wasm-gc and is how linear memory is accessed.
- Current idioms the compiler insists on: `#derive(Eq, Debug)` (before the type) on a public type needs a `pub extend T with ...` entry in the package's `extends.mbt` (copy a neighbouring one); `extend` is a keyword; `Ref(x)`, `Map([], capacity=n)`, `Array(capacity=n)`, `@cmp.minimum`; `try?` is gone (`try Some(e) catch { _ => None }`). In a function with a bare `raise`, `catch` can match constructors of several suberror types.
- Script mode (`moon run x.mbtx`) currently fails with a core `gzip` alias conflict, so automation stays in Node scripts under `bench/`.

## 4. Architecture

Dependency direction (never reverse): `core ← pbf ← mvt ← tess/style ← worker`, `core ← geom ← formats/tiler ← geojson_tiles ← geojson_worker`, `formats ← data_worker`, `pbf ← formats ← services_worker`, `core/geom ← xml ← kml ← xml_worker`, `tiff ← geotiff_worker`, `style/tiler ← cluster_props ← geojson_props_worker` (the GeoJSON module with expressions), `formats ← data_worker`, `geom/xml ← kml ← xml_worker`, `tiff ← geotiff_worker`, `geom ← analysis ← analysis_worker`, `geom/clipper ← overlay ← geometry_worker`, `geom ← relate ← relate_worker` (which also takes `@analysis.Index`), `geom ← robust ← (hull, delaunay)`, `geom ← (simplify, hull, delaunay, lineops) ← shapes_worker`, `geom ← (clusters, grids, isolines) ← surface_worker`, `core ← density ← surface_worker`, `core ← viewshed ← viewshed_worker`, `geom ← route ← route_worker`, `proj ← proj_worker`, `core ← geodesic ← geodesic_worker`, `core ← render_webgl2 ← map ← bundle/main ← (npm, element) ← adapters`, and the wasm-gc-only `wasmio ← (geojson_tiles, *_worker entries)`. Nothing under `map/` may depend on a UI framework.
Planned data/analysis/3D packages (VISION §3) ship as separate npm entry points with their own lazily loaded wasm and size budgets: `map` must never import them, and they exchange data with the display only through columnar (GeoArrow-compatible) buffers. Granularity (decided in Phase 6.5): one wasm module per entry, run in its own lazily started worker; split a feature group into its own module once its own code exceeds ~20KB gzip (each module duplicates ~6KB of core: trig, int formatting). Never link analysis into the display worker. A new entry or module needs a row in `npm/scripts/size.mjs`.

- `core`, `pbf`, `mvt`, `tess`, `style` are pure MoonBit and must pass tests on every backend.
- `worker` ships as **wasm-gc** (decided in Phase 0). Tile bytes and output buffers cross the JS boundary through a linear-memory region managed by the worker, using inline-wasm load/store. Keep that wasm-gc-specific I/O inside wasm-gc-only packages: `wasmio` (input at `PAGE`, output after it, `MAX_INPUT_BYTES` for every entry, f64 input read as is by `input_f64s`; the entries wrap its functions in their own `#export_name`s, which imported packages do not export) serves every wasm-gc-only entry (and `geojson_props_worker` the host's `Number`, `String` and `Intl` for expressions, `wasmio/text.mbt`), and its JS side `wasmio/js/host.mjs` gives them `hostNumber` and `writeInput`. An all-targets package cannot import a wasm-gc-only one, so `worker` (and the bench entries) keep their own few load/store helpers. Do not pass data element-by-element through exported functions: per-element calls on GC arrays were 5–50× slower in Phase 0 benchmarks.
- Tile pipeline: `map` (main thread) asks a worker for a tile → `worker/js/worker.mjs` fetches it, places it in linear memory and calls the wasm-gc exports of `worker` (`prepare_input`, `init_style`, `process_tile`, `output_addr`) → `TileProcessor` decodes, tessellates and packs every fill/line layer of the style into one `PackedTile` blob (header of `LAYER_ENTRY_WORDS` u32s per layer, named `ENTRY_*`, Int16 positions, 16- or 32-bit indices, coordinates rescaled to `@core.TILE_EXTENT`, MapLibre's 8192; layers with the same geometry, like a road and its casing, share one buffer) → the glue slices it into ArrayBuffers and transfers them → `render_webgl2` uploads them as they are. In wasm-gc the blob is written in place in linear memory (`store_memory.mbt`); other targets use an array (`store_array.mbt`). The linear-memory files are wasm-gc only: in the wasm backend MoonBit's own heap lives in linear memory. The main thread never touches geometry (VISION §4-3).
- `map` must not import `worker` (it would pull mvt/tess into the main bundle); shared constants live in `core` or are mirrored with a pointer to the original. `style` compiles filters and paint into `Expr` (the subset in `style/expr.mbt`, nesting capped by `MAX_EXPR_DEPTH`) and reports anything else as `Unsupported` with its JSON path. Unless `strict`, `Style::from_json` leaves such a property out and parses the layer again (a layer or source that still cannot be drawn is dropped) and lists each in `warnings`. Only the main thread parses and compiles styles: display workers get the result as bytes (`Style::to_compiled` / `from_compiled`, `style/compiled_writer.mbt` and `compiled_reader.mbt` with the `EXPR_*` tags, docs/FORMATS.md "Compiled style"; query filters through `write_expr` / `read_expr`), which keeps the parser and compiler out of the worker wasm (about 22KB gzip). The main thread alone adds the properties parsed but not drawn yet (`ignored_properties`, `Style::report_ignored`), which the facade fires as `warning` events. `npm run style:compat` lists what public styles (`bench/style/public-styles.mjs`) lose that way; `Expr::eval` is generic over a `FeatureContext`. Compiling for a type annotates as MapLibre's parser does (an assertion, or `to-color` for colors, around an expression of type `value`), `let`/`var` are inlined (`MAX_EXPR_NODES` caps the expanded size), and MapLibre's evaluation errors are `Value::Failed`, which a property reads as its default. A `FeatureContext` brings the host's `Math` (`trig`), JavaScript's `String(number)` / `Number(string)` (`number_text`, `text_number`) and `Intl` (`number_format`, `collate`, `resolved_locale` for `number-format` and collators; `style/intl_js.mbt` calls it on the js backend, `@style.Intl` carries it into the worker): the display worker passes them in through `host.*` imports (`wasmio/js/host.mjs` `hostText`, `intl`), which keeps float printing and `strconv` out of it. `global-state` is compiled to the value the style's `state` gives (`with_global_state`): the facade keeps the global state (`setGlobalStateProperty`) and hands the engine the style with those values as defaults, so layers reading a changed key differ by `same_tiles` and are drawn and loaded again. `format` evaluates to `Value::Formatted`; the worker packs its sections with their `font-scale` and `vertical-align` and `worker/js/text.mjs` shapes them as MapLibre's `shapeLines` (sections' `text-font` and `text-color` are drawn too, below). `is-supported-script` is always true, as in MapLibre 6.16 (no host there sets `isSupportedScript`). `within` and `distance` (ports of style-spec's, cheap-ruler and tinyqueue included) read the feature's geometry in its canonical tile through `FeatureContext::within` / `distance`: the display worker's `FeatureRef` loads it as MapLibre's `loadGeometry` (`@style.GEOMETRY_EXTENT`, tile x and y from the tile message) for filters, layout, per-vertex paint and queries; elsewhere they give false and NaN as MapLibre without a canonical tile, so paint drawn by groups on the main thread (symbols, extrusion color, layers reading feature state) refuses them as `Unsupported`. Legacy filters and property functions never reach the engine: the facade converts them with the lazily loaded `legacy.js` (`npm/src/legacy.ts`, a port of style-spec's `convertFilter` / `convertFunction`; `isLegacyFilter` / `hasLegacy` in `npm/src/style.ts` decide whether to load it).
- Fill outlines (`fill-antialias`, default true; `fill-outline-color`, default the fill color): tess emits each ring's edges as a line list (an open ring gets its closing edge), packed after the fill's triangle indices; the renderer draws them with `gl.LINES` and MapLibre's fill-outline shader (alpha from the pixel's distance to the line), after the fill, with the outline color in the stroke-color slot. `npm run style:golden` matches MapLibre exactly on fills.
- Dashed lines (`line-dasharray`, constant or by zoom; by feature below): tess records each vertex's distance along its line (`LineBuffers.distances`, in `TILE_EXTENT` units, even as MapLibre's `linesofar`; sharp corners split and restarted past `MAX_LINE_DISTANCE` as its line bucket does) only for dashed layers, which share buffers only with dashed layers; the worker packs them as u16 per vertex. The main thread keeps MapLibre's `LineAtlas` (`render_webgl2/line_atlas.mbt`, byte-identical) and draws with its line_sdf shader (`lineDash` program, `a_dist` at location 13): pattern and `line-floorwidth` at the integer zoom, edges smoothed over the shorter of that pattern and the one a zoom away, as MapLibre at rest (no cross-fade animation). A data-driven dasharray (`StyleLayer::feature_dashes`; not with feature state or in layers drawn by groups) is evaluated per feature at the tile's zoom and either side and packed as patterns plus four u16s per vertex (docs/FORMATS.md "Packed tile"; such layers never share buffers); the main thread puts the patterns in the atlas and uploads per vertex row, height, width (truncated, as MapLibre's Uint16 `a_dasharray_*`) and both edge lengths (`lineDashFeature`, `a_dash` at location 15).
- Style images and patterns: the facade keeps the images' names and hands their straight RGBA pixels to the engine (`Map::add_image`; `addImage`, `updateImage`, `removeImage`, `loadImage`, `styleimagemissing` as MapLibre's); a style's `sprite` (one URL or `{id, url}` list, @2x on a 2x screen) is read by the lazily loaded `sprite.js` (`npm/src/images.ts` is the import-free part). The main thread packs images into one `PatternAtlas` as patterns are first drawn (shelves, 1 px wrapped padding as MapLibre's `ImageAtlas`; cleared when images change) and draws `fill-pattern` and `background-pattern` with MapLibre's fill_pattern, fill_outline_pattern and background_pattern shaders, positioned by the tile's world pixel at the integer zoom (`Placement.pattern`); the pattern is taken at the integer zoom (no cross-fade). A pattern picked by feature draws the layer by groups (`StyleLayer::paints_by_group`). Fill outlines go after all of a tile's fills, as MapLibre draws them. Icons have their own atlas (`Renderer::icon`: 1 px transparent padding, MapLibre's `ImageAtlas` for icons), whose places never move: an image replaced at the same size is copied over its pixels, one of another size gets a new place. The workers lay icons out, so they are told each image's size (`Map::send_images`, once per frame with changes); tiles whose icons used a changed image are loaded again, and while the facade loads a sprite (`Map::hold_images`) the workers hold tiles of styles with icons, as MapLibre's tiles wait for the sprite. An image a tile lacks fires `styleimagemissing` once (`Map::report_missing`). `line-pattern` (MapLibre's line_pattern: as tall as the floor width, along the line distances, `StyleLayer::line_distances`) and `fill-extrusion-pattern` (fill_extrusion_pattern: walls by their distance along the ring, packed in the extrusion vertex, and height) are drawn too.
- Translucent or patterned extrusions are drawn as MapLibre does: all of the layer's meshes into depth first, then color with a stencil count so each pixel takes its nearest surface once (coincident roofs included); the context has a stencil buffer for it.
- Line gradients (`line-gradient` over `["line-progress"]`, which no other property may read; a GeoJSON source's `lineMetrics`): the tiler ports geojson-vt's line metrics (each line its own feature, slices keeping where they lie along it; `CLIP_START`/`CLIP_END` properties; `npm run geojson:golden` compares them). Gradient layers record each vertex's share of its line (`LineBuffers.progress`, sharp corners split) and a row per line with its clip, packed per entry; the main thread builds MapLibre's `renderColorRamp` per mesh (`color_ramp`, `ramp_width`, evaluated through `JsProps.progress` so `Expr::eval` stays one instantiation: another `FeatureContext` cost 24KB gzip) and draws with its line_gradient shader (`lineGradient`, `a_progress` at location 14).
- Heatmaps (`heatmap` layers; `["heatmap-density"]` only in `heatmap-color`, `Invalid` elsewhere): the worker packs them as circles (`KIND_CIRCLE`, its own buffers), weight and radius per vertex in the opacity and size slots (`SLOT_WEIGHT`), or by group and state range when they read feature state, as circles. The main thread ports MapLibre's two passes (`map/heatmap.mbt`, `render_webgl2/heatmap.mbt`): kernels added (`ONE, ONE`) into an RGBA16F texture a quarter of the viewport (RGBA8 without `EXT_color_buffer_float`), unclipped, each tile once (an ancestor standing in draws instead of its children), then colored over the viewport through a 256-px `color_ramp` evaluated via `JsProps.density`. On terrain each terrain tile gets its own kernels at 512 px, as MapLibre's per-tile framebuffers (cut at tile edges). Ramps are uploaded premultiplied in JS as MapLibre's `premultiplyAlpha` rounds. Queries hit points within the radius on the map.
- Data-driven paint of fills, lines and circles goes per vertex (decided in Phase 15): `@style.StyleLayer::vertex_paint` lists the data-driven properties with the outputs at each stop of their top-level zoom curve (so a z14 tile drawn at z18 is exact, as MapLibre is only after re-parsing overscaled tiles); the worker evaluates them per feature and repeats the words over its vertices (`Store::repeat`, a doubling `memory.copy`), each layer with its own buffer also over shared geometry; the renderer points the slot attributes (`a_color_lo`/`hi`, `a_opacity`, `a_extent`, …) at the stop below the current zoom and mixes with `u_t`, and passes constant paint through the same attributes with `vertexAttrib*`, so there are no shader variants. Lines put `line-gap-width` and `line-offset` in the circles' stroke opacity and width slots (`SLOT_GAP_WIDTH`, `SLOT_OFFSET`) and are drawn with MapLibre's line shader math (outset, inset, blur); an offset layer's vertices carry MapLibre's `a_offset_normal` (`LineBuffers.offsets`, packed per entry, `a_offset` at location 2), so it shares buffers only with offset layers. `*-translate` (a constant or zoom curve over `[x, y]`, `@style.translate_at`) moves a layer's tile matrix (`Map::translated`, MapLibre's `translatePosition`) and its queries. `*-sort-key` orders a layer's features in the worker (`feature_order`, `@core.stable_order`, ties in tile order) and such layers never share buffers; circles with one are drawn across tiles in key order from the runs each entry packs (`Map::draw_circles_by_key`). `same_tiles` compares the baked paint. Layers reading feature state, symbols and extrusions still split features into groups by the values their paint reads (`feature_inputs`, at most `MAX_GROUPS` per layer and tile), an entry per group carrying those values; the main thread evaluates paint per group at the current zoom. The main thread evaluates through one context type (`JsProps`), so `Expr::eval` is compiled into the bundle once.
- Runtime style changes: the facade edits a copy of the style document (`npm/src/style.ts`, import-free) and hands the whole of it to `Map::set_style` (`map/style.mbt`), which keeps a source's tiles when `Source::same` holds and each of its layers in the new style has a `StyleLayer::same_tiles` twin (by id) in the old one, renumbers their meshes by layer id, and otherwise marks tiles `Stale` (drawn until reloaded); workers get `{type: "style"}`. GeoJSON data is compared by identity (`keepGeoJSONData` restores it for equal data), and changed sources are reloaded with `reload_source`. Layers with `visibility: none` are dropped when parsing, so hiding one is a removal.
- Feature queries: the display worker keeps each vector or GeoJSON tile's bytes it sent (until `{type: "drop"}`), and `map/query.mbt` sends each drawn tile a query (docs/FORMATS.md "Query") that `worker/query.mbt` answers as MapLibre's `FeatureIndex` would (`@core.polygon_hits_*`, ports of its intersection tests; the tile's query padding; extrusions projected and hit in 3D); labels are found on the main thread from the boxes of the last placement and named to the worker by feature index. The facade orders the hits (`npm/src/query.ts`, MapLibre's merge and 3D sort), so queries return Promises; `querySourceFeatures` gives each feature the source tile it came from as `tile: {z, x, y}` (MapLibre's canonical tile), which the showcase's route uses to cut each road to its own tile. Buckets take geometry types as MapLibre's do (fills and extrusions fill lines too; circles go on every vertex).
- Feature state: paint may read `["feature-state", key]` (`Expr::FeatureState`; `FeatureContext::state`, None in the worker). For layers whose paint reads it (`StyleLayer::reads_state`), the worker records each feature's index range per packed entry with its id (`feature_ranges`; the source's `promoteId` or the tile's / GeoJSON id), which the glue keeps; such layers never alias another's buffers. The facade holds the states and hands each feature's to `Map::set_feature_state`, which asks the workers where the stated ids lie (`{type: "ranges"}`) and draws those ranges with their state (`draw_by_state`, `Renderer::set_range`); `idle` waits for the answers.
- Raster tiles and where tiles come from: a `raster` source's tiles are decoded by a display worker into ImageBitmaps (`KIND_RASTER`, layer -1 like DEM tiles) and drawn with MapLibre's raster shader without its fade, on the pixel grid at rest (`Transform::tile_matrix(aligned=true)`, MapLibre's `alignedProjMatrix`; `npm run raster:golden` must stay pixel-identical). Sources given by `url` are completed by the facade (`npm/src/tilejson.ts`, documents cached, sources still loading left out of the engine's style); `pmtiles://` archives get their header read by the lazily loaded `pmtiles.js` and their tiles by the worker (`worker/js/pmtiles.mjs`, a port of pmtiles' reader with capped sizes; `npm run pmtiles:golden` against pmtiles 4.5.0). `bounds` and `scheme: "tms"` are applied by the engine, and tile templates take MapLibre's placeholders (`{bbox-epsg-3857}` for WMS and ArcGIS `export`, `{quadkey}`, `{ratio}`, `{prefix}`; `npm run raster:golden` compares the URLs requested); `transformRequest` reaches tile fetches as the message's `init`.
- Image, video and canvas sources (MapLibre's `ImageSource`, `VideoSource`, `CanvasSource`): the facade loads `media.js` (`npm/src/media.ts`, import-free) with the first style that has one; it fetches images (no credentials, http(s) against the style URL, `transformRequest` as `"Image"`), makes muted looping `<video>`s, finds canvases by `getElementById` (or takes the element `addSource` was given), and computes where the picture goes as MapLibre does (`quadOf`: the center tile, corners rounded in 8192 units, `calculateImageWarp`). The engine (`map/media.mbt`, style kind `Image`) uploads the picture without mipmaps, premultiplied, and draws it with the raster shader, whose corners (`u_top`, `u_bottom`) and warp (`u_warp`) MapLibre's tiles take too, over its tile unclipped (16 x 16 quads when MapLibre subdivides). A playing video or animating canvas is uploaded every frame and keeps frames coming, but unlike MapLibre the map still goes idle. `npm run style:golden`'s `images` scenes must stay pixel-identical.
- Custom layers (MapLibre's `CustomLayerInterface`): `addLayer` puts a placeholder `{id, type: "custom"}` in the style document (so ordering, `moveLayer`, `beforeId` and removal are ordinary edits; `getStyle` leaves it out, a new style drops it as MapLibre's `setStyle` does) and hands the layer to `custom.js` (`npm/src/custom.ts`, import-free, loaded with the first one; `onAdd` runs then). The engine (style kind `Custom`, `map/custom.mbt`) calls one JS renderer where the layer sits, `prerender` before the frame is cleared, with `Map::custom_numbers` (`Transform::world_matrix` is MapLibre's `modelViewProjectionMatrix`, `npm run camera:golden` compares it); `custom.ts` builds MapLibre's options (`defaultProjectionData.mainMatrix` for Mercator 0 to 1, `getProjectionData`, the Mercator shader prelude), saves the GL state, sets MapLibre's custom-layer defaults and depth mode ("3d" tested, "2d" off) and restores the state after the layer's code. Custom layers are drawn over terrain, never into its textures.
- Screen tracking and image export: `Map::locate` projects a place onto the terrain and asks `Transform::occluded` whether the terrain hides it (ports of MapLibre's `isLocationOccluded` and its CPU ray march over the terrain, `core/occlusion.mbt`, through a `@core.Terrain` of the loaded DEM tiles: heights read across tile borders as MapLibre backfills them, flat 0 m where no DEM has loaded); `unproject` with terrain marches the same ray. The facade's `track` locates every tracked place in one `map_locate` call after each frame (`Render` listeners). `toBlob` waits for `idle`, then `Map::render_region` draws the current tiles into an offscreen framebuffer (`Renderer::begin_offscreen`) part by part: a `Window` matrix maps the whole image's clip space to the part's (the sky's horizon is moved by the part's offset), and the facade joins the parts in a 2D canvas.
- Camera math and tile covering live in `core` (`Transform`), pure and tested on all targets; `map` only wires DOM events, workers and the frame loop (renders on demand, falls back to a loaded ancestor or loaded children). The camera has bearing and pitch (≤ `MAX_PITCH` 85°, as MapLibre). Above about 70° the horizon comes on screen: the ground ends at MapLibre's horizon line (`Transform::horizon`, 85% of the way to the true horizon), screen points above it map to the ground at the line, the far plane sits at its depth, and the style's `sky` is drawn above it (MapLibre's sky shader; no `sky`, no sky or fog, as in MapLibre). `Transform` keeps a MapLibre-style view-projection (`Mat4`, column-major) over world pixels relative to the center, so precision holds at every zoom. `covering_tiles(min_z, max_z)` walks a quadtree over the view's ground footprint and drops a zoom level per doubling of distance beyond `LOD_DISTANCE` camera distances, and leaves ground that wants more than `MIN_ZOOM_SLACK` levels below `min_z` empty; leaves never overlap. Shaders take a per-tile `mat4`; lines extrude in tile units (they thin with distance) and scale their antialiasing by depth; an ancestor standing in for a missing tile is clipped in the fragment shader (`u_clip`, tile units), since scissor rectangles fail once the map turns. Circles (`KIND_CIRCLE`) reuse the line vertex layout, one quad per point inside the tile (`@tess.add_points`); the shader expands it as MapLibre's circle shader does: around the projected center on screen, or on the map (`circle-pitch-alignment`), scaled by depth or kept on screen (`circle-pitch-scale`).
- Camera moves are MapLibre's: `core` ports its default constrain (zoom raised until the latitude limit, ±85.051129°, and `maxBounds` fill the view; the zoom set before the center, a move's end point constrained once as `applyConstrain` does), `easeTo`, `flyTo` (van Wijk and Nuij), `cameraForBounds`, `setLocationAtPoint`, `project` / `unproject` / `getBounds` and the CSS `ease` curve (`Bezier`); `npm run camera:golden` drives MapLibre's own `Camera` in Node with frozen time (`setNow`) and must stay within 1e-6 px, 1e-7°, 1e-8 zoom. `map` runs animations in the frame loop (`step_animation`), keeps `move_start` / `move_end` around gestures, inertia (MapLibre's buffer and decelerations), wheel zoom (ended 200 ms after the last wheel) and animations, and has MapLibre's handlers (`Handler`; 3 px click tolerance, keyboard, double click, shift-drag box zoom, two-finger pitch). The main thread draws extrusion layers on screen (never into terrain textures) with MapLibre's fill_extrusion shader and the style's `light`, depth-tested (a depth-only pass first when translucent); on terrain each feature stands on the ground under its centroid (looked up like label heights, `ExtrusionGround`).
- Binary forms that cross workers (group properties, columnar tiles, `Table` bytes; docs/FORMATS.md) are written and read with `@core.ByteWriter`/`ByteReader` (sticky errors) and share the `@core.PROP_*` value tags. Group properties are binary, not JSON, because stringify pulled float printing into the worker; `worker/js/worker.mjs` decodes them into prototype-less objects. Layers share buffers when their filters are written identically (`filter_id`), not by comparing `Expr`s.
- `mvt` decodes layer tables, feature headers and tags in `Tile::parse` (raising `MvtError` once per tile) and stores features column-wise; per-feature calls take an index (`layer.decode_geometry(i, out)`, `layer.property(i, key)`) and don't raise. Geometry is decoded lazily into a reusable `Geometry` buffer.

Backend facts measured so far (see PROGRESS.md):
- **In wasm-gc every call to a `raise` function allocates its result object, even on success.** Keep `raise` off hot paths: report errors through sticky state or return values, and raise only at coarse boundaries. This alone made the mvt decoder go from 1.3–2.2× slower than JS to faster than JS.
- wasm (linear memory) uses refcount + TLSF and is 6–9× slower than wasm-gc/JS on allocation-heavy code.
- `wasm-opt -O3` made the wasm-gc mvt decoder 12–45% *slower* in every browser; do not run it on wasm-gc builds. For wasm (linear memory) it helps only on Node 22, whose older V8 does not inline small wasm functions (flags in `bench/backend/opt.mjs`).
- In hot loops `FixedArray` beats `Array` (an `Array` access also loads and checks its length): switching earcut's node pool cut its time by about 25%. Prefer incremental rotation over per-vertex `sin`/`cos`/`atan2` (it made line extrusion about 40% faster).
- V8 does not switch a running wasm call to optimized code, so a worker's first tile runs in baseline code (about 3–5× slower than warm). Warming up with a synthetic tile at init did not help first render in measurements and was removed.
- Sharing one buffer between layers with the same geometry and packing in place instead of copying made `process_tile` 23–27% faster (median tile) and the output 17% smaller. Compiling the worker wasm once on the main thread and sending the module to every worker made no difference to first render and was reverted.
- Line output size matters more than tessellation speed: round caps are square extensions that the line shader cuts with `length(side, along)`, and layers with at most 65536 vertices use 16-bit indices; together they cut the center tile's packed size from 2.0 MB to 0.8 MB and `process_tile` from 5.4 to 3.2 ms.
- Bundle size: `Repr`/`Debug` output and `@string.parse_double` (strconv) pulled about 28KB gzip into the main bundle (49.1 → 20.6KB once removed); shipped code reports errors with `message()` strings instead. A second instantiation of `Expr::eval` cost about 11KB minified but only 0.2KB gzip.
- Copying linear memory into GC `Bytes` is fast when done 4 bytes per load into a `FixedArray[Byte]` and reinterpreted (`bench/entry/linear_memory.mbt`); `Bytes::makei` calls a closure per byte and is 2–6× slower.

## 5. Benchmark gotchas

- Headless Chromium defaults to SwiftShader; GPU benches must launch with `--use-angle=metal --enable-gpu --ignore-gpu-blocklist`.
- On the M2 dev machine frame time is vsync-capped at 16.67ms even for MapLibre; use per-frame render CPU time (and `--uncapped`) as the proxy metric. Real Android measurement is out of scope for now.
- Bundling MapLibre `src/` with esbuild requires `useDefineForClassFields: false` and an alias to `node_modules/maplibre-gl/src` (package `exports` blocks deep imports).
- Inline `<script type="module">` in bench pages did not execute under Playwright; keep page code in external `.mjs` files.
- Register MapLibre `load`/`idle` listeners immediately after constructing the map (idle can fire in the same task as load).
- Never pass tile templates through `new URL()`: it percent-encodes `{z}`/`{x}`/`{y}` and every tile 404s (MapLibre then draws an empty map quietly, which voided the render comparisons until Phase 9.2). Check that both engines draw before trusting a comparison.
- `bench/fixtures/gsi-bvmap/` (~13MB) is gitignored; only the manifest is committed. Attribution: 国土地理院ベクトルタイル提供実験.

## 6. Testing conventions

- Golden data: compare against existing JS implementations (@mapbox/vector-tile, earcut JS) via scripts in `bench/` or `test/fixtures/`. Tessellation must also check that total triangle area equals polygon area.
- Every `pub fn` gets ≥1 direct test; every error path (`raise`, `None`) is covered. Tests run on all backends.
- Prefer `assert_eq` (or `assert_true(x is Pattern(...))`) over snapshots for stable results; derive `Debug` + `debug_inspect` for structured output.
- A test that only re-runs the type checker (`let _ = …`) duplicates `moon check`; delete it.
- Fixtures from external sources carry their attribution (fixtures README and `NOTICE`).

## 7. Refactoring checklist

When the user says **「リファクタリング」 / "refactor" / "tidy up" / "clean up"**, walk these lenses **in order** and write a concrete findings list **before** changing code (consider the `moonbit-refactoring` skill). This applies whether the target is one file or the whole tree.

### 7.1 Constants
Promote magic numbers and repeated literals that name a concept to a `pub let` in the owning package, defined exactly once. Examples: MVT and packed extents (`@core.TILE_EXTENT`, VISION §4-2), protobuf wire types and field numbers, Style Spec keys, vertex attribute layouts and strides, Worker message type tags.

### 7.2 Duplicate / dead code
- Consolidate identical helpers in the lowest package that may own them, respecting the dependency direction in §4.
- Delete stub files that are comment-only `.mbt` files once a package holds real API.
- Drop unused imports (`unused_package`).
- Make `pub` items with no external caller private, or delete them.
- Exception: the intentional duplicates in `bench/backend` (§4).

### 7.3 File splitting
A `.mbt` file over ~500 lines is a smell, not a rule. Split only at a logical boundary (e.g. varint reader vs message walker; earcut vs line extrusion), never to hit a line count. Keep blackbox (`*_test.mbt`) and whitebox (`*_wbtest.mbt`) tests separate.

### 7.4 Test adequacy
- §6 holds: golden tests at every decode/tessellation boundary, the area check for tessellation, and every error path covered.
- Tests assert on values, not just shapes.
- Tests pass on all four targets.

### 7.5 Performance
Invariants:
- Hot paths (pbf/mvt decode, tessellation, worker packing, per-frame rendering) stay allocation-free and write into preallocated `FixedArray`/`Bytes` (VISION §4).
- A refactor touching a hot path reruns the relevant bench and records any regression in PROGRESS.md before merging.
- Bundle size is a budget (VISION §2), so a refactor must not add dependencies or runtime code to the main-thread bundle without measuring.

Speed opportunities — every refactor also looks for measurable wins in the code it covers:
- Find the cost first: profile or break the bench down (per-stage rows, `--output-wat` for wasm-gc) instead of guessing. Known traps: `raise` on hot paths, `Array` vs `FixedArray` in tight loops, per-element boundary calls, per-vertex trig, oversized output (§4).
- List each candidate with its expected effect before changing code; keep a change only if the bench shows a win beyond run-to-run noise on the target browsers and no regression elsewhere.
- Record what was tried in PROGRESS.md, including changes that did not help and were reverted, so they are not retried blindly.

### 7.6 Documentation freshness
- PROGRESS.md and VISION.md match the code state.
- Public APIs have `///` doc comments.
- `.mbti` is regenerated and its diff is the intended public-API change.

### 7.7 Comment hygiene
**The default is no comment.** Comment only where a reader cannot recover the intent from the code. Keep it to one or two lines, three at most. `node bench/lib/long-comments.mjs` lists the blocks over three lines.

- **Delete what the code already says.** If code needs a paraphrase, fix the code instead: use a better name, a named intermediate, or a smaller function.
- **Delete documentation that wandered into source.** Design rationale and package tours belong in VISION.md, PROGRESS.md or README. The source may cite them but must not restate them. File-header essays and section banners are this failure mode; `///|` already separates blocks.
- **Delete narration of the past** (what used to happen, what a commit changed). If a bug explains a non-obvious line, keep the reason in one clause and cite the issue (`#N`).
- **Keep the constraint the code can't show**: a spec rule (MVT spec section, Style Spec property, WebGL2 limit), an invariant the compiler doesn't enforce, or a deliberate deviation.
- **No phase codes in comments** (`Phase 2`). Name the thing instead. Issue numbers and spec section references are fine.
- No comments between the items of an enumeration: enum variants, struct fields, TS interface members, array and object literals, tables of cases (MoonBit, TS and JS alike). Describe the items in the doc comment above the whole (e.g. "`a`: ..., `b`: ...") or next to the code that uses them.
- Tests get the same treatment: the test name says what it asserts.

### 7.8 Latest MoonBit language-spec conformance
- Migrate deprecated constructs rather than suppressing the warnings.
- Verify constructs against `moon ide doc`, the `moonbit-orientation` skill and local sources, not memory.
- Adopt current idioms where they help clarity: `raise` error handling, pattern-match views, labelled/optional args, method syntax, iterators, derive macros.
- If a `moon` version bump changes formatting or generated output, land that diff on its own.

### 7.9 Validation loop after refactoring
```sh
moon check --target all --deny-warn
moon test --target all
moon fmt
moon info
```
Then run the §8 security check on the touched area. Push only when everything is clean.

## 8. Security check

Run this when the user says **「セキュリティチェック」 / "security check"**, as part of every refactor (§7.9), and before adding or upgrading any dependency or cutting a release. Report findings as a list (severity, location, fix) before changing code.

### 8.1 Dependencies and supply chain
- `npm audit` in every directory with a `package.json` (`bench/`, `npm/`). Also check GitHub Dependabot / security advisories for the repo: `gh api repos/{owner}/{repo}/dependabot/alerts`.
- Recent advisories move faster than `npm audit` sometimes reflects. For each direct dependency, check its GitHub Security Advisories and release notes for the pinned version, especially MapLibre, Playwright, esbuild, binaryen and anything in the shipped bundle.
- Pin exact versions (`--save-exact`) and commit the lockfile. CI uses `npm ci`, never `npm install`.
- Before adding a package, check its maintainer, download history, install scripts (`preinstall`/`postinstall`), and whether it is a typosquat. Prefer no new dependency when a few lines will do (bundle budget, VISION §2).
- MoonBit deps (`moon.mod` `import`): pin versions, and review the source of new mooncakes packages (`moon fetch`) before depending on them. Keep the toolchain current with `moon upgrade` and record the version in PROGRESS.md.
- Never pipe a remote script to a shell, and never run downloaded code from its own directory. Fixtures and downloaded tiles are data: verify them against the sha256 manifest.

### 8.2 Untrusted input (tiles, styles, GeoJSON, URLs)
Everything fetched at runtime is attacker-controllable. Decoders must fail safely on malformed input:
- **pbf/mvt**: bounds-check every read. Reject varints longer than 10 bytes and length-delimited fields that exceed the remaining buffer. Cap nesting, feature, key and value counts. Make sure no input can produce an infinite loop (zero-length fields, `ClosePath`/`MoveTo` command counts of 0 or huge).
- **tess**: cap vertex and index counts per tile, guard against degenerate or self-intersecting rings blowing up earcut, and check that integer math on quantized coordinates (Int16, VISION §4-2) cannot overflow silently.
- **style**: expression evaluation is bounded (depth, array sizes); no `eval`/`new Function`. Unknown expressions fail with a diagnostic, never execute.
- **GeoJSON**: limit size and coordinate count before tiling. `JSON.parse` only, and keep `__proto__` keys out of property maps (prototype pollution).
- **worker linear memory**: raw-address load/store in `worker/` must validate every offset and length against the region it owns. A bad length must never read or write outside it. This is the one place where MoonBit's bounds checks don't protect us.

### 8.3 Web platform
- No `innerHTML`/`outerHTML`/`insertAdjacentHTML` with data from tiles, styles or attributes. Use `textContent` and DOM APIs, which matters most for future labels and attribution strings in `<mb-map>`.
- Work under a strict CSP: no `eval`, no `new Function`, and workers loaded from same-origin URLs (no blob or data-URL workers unless documented).
- Fetches for tiles, styles and sprites send no credentials by default. URL templates may only substitute MapLibre's placeholders (`{z}/{x}/{y}`, `{prefix}`, `{ratio}`, `{quadkey}`, `{bbox-epsg-3857}`, `{bbox}`; `TILE_PLACEHOLDERS` in `npm/src/urls.ts`, `tile_url` in `map/dom.mbt`), with no open redirects or arbitrary schemes. Any request transform hook is the caller's responsibility and documented as such.
- `postMessage` handlers check message shape and type and ignore unknown messages.
- `<mb-map>` attributes (`style-url`, `center`, …) are parsed strictly; invalid values are rejected, not coerced.

### 8.4 Repo and tooling hygiene
- No secrets, tokens or personal data in code, fixtures, bench results or commit messages. Bench results record the environment, not user identifiers.
- `bench/lib/serve.mjs` is a dev-only server: it must bind to `127.0.0.1`, refuse paths outside the repo root and dotfiles (`.git`, `.env`), and survive malformed URLs. `bench/lib/serve.test.mjs` pins this down.
- Ported code keeps its license header and a `NOTICE` entry (VISION §7). License review is part of the dependency check.

## 9. Claude Code on the web

Sessions on claude.ai/code run in a fresh Ubuntu 24.04 VM (4 vCPU, 16 GB) with the repo cloned; Node 22, `gh` and Chrome are there, MoonBit is not.

- **Setup**: `scripts/setup.sh` installs the MoonBit toolchain pinned in `scripts/toolchain.env` (sha256-checked), runs `npm ci` in `npm/`, `bench/` and `examples/react/`, installs Playwright's Chromium and fetches the GSI fixtures (`--no-fixtures`, `--no-browser` skip those); it is idempotent and CI runs it too. The environment needs network access to `cli.moonbitlang.com`, `cyberjapandata.gsi.go.jp`, `tiles.openfreemap.org`, `build.protomaps.com` and `raw.githubusercontent.com` (the public styles' tiles and sprites) Playwright's CDN (`cdn.playwright.dev`, `playwright.download.prss.microsoft.com`) and, for `npm run services:golden`, the public services in docs/CLOUD.md besides the default list; Node's `fetch` reaches them only with `NODE_USE_ENV_PROXY=1`: set the environment's network access to Custom with those domains plus the default package managers, or Full. Run it from the environment's setup script or a SessionStart hook (docs/CLOUD.md has both); if `moon` is missing when a session starts, run `scripts/setup.sh` first.
- **What carries over**: only the repo. Local auto-memory and user-level plugins do not reach the web, which is why §2's standing instructions live here; the `moonbit-skills` plugin is absent, so check MoonBit APIs with `moon ide doc`, the generated `.mbti` and docs.moonbitlang.com (§3).

- **GitHub**: pushes go through a proxy (branch deletions and tags are refused). If a push to `phaseN/...` is refused, use the branch name the session suggests.
- **Parallel work**: one web session per line of work is the dependable way; `isolation: "worktree"` subagents may work too but are untested there.

## 10. Things to avoid

- ❌ Planning docs outside VISION.md / PROGRESS.md.
- ❌ Reversing the package dependency direction, or UI-framework dependencies under `map/`.
- ❌ Allocation in hot paths without a measured reason.
- ❌ Perf claims without a `bench/` script and a results JSON.
- ❌ Adding dependencies without the §8.1 check and a note in PROGRESS.md.
- ❌ Trusting tile, style or GeoJSON input (see §8.2).
- ❌ Suppressing deprecation or `unused_*` warnings instead of fixing them.
- ❌ Skipping `moon fmt` / `moon info` before committing, or bypassing hooks with `--no-verify`.
